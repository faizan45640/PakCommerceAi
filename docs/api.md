# API Reference

The Express backend in `apps/api`, running on port 4000.

Base path: `/api/v1`

---

## Authentication

Every protected endpoint (`/api/v1/products`, `/api/v1/inventory`, `/api/v1/orders`,
`/api/v1/customers`, `/api/v1/copilot`, …) requires a Supabase access token:

```http
Authorization: Bearer <access_token>
```

The token is the one `supabase.auth.signInWithPassword()` returns in the browser. The API
verifies it with Supabase — it does not decode and trust it locally — and then builds a
**request-scoped database client that carries it**.

That last part is the whole design. The API does **not** filter results by seller. It hands
the seller's identity to Postgres, and the RLS policies written in the migrations do the
filtering. There is no `where seller_id = …` anywhere in the product code, and there must
never be one: that would turn a rule the database enforces into a rule a developer has to
remember on every query.

Consequences worth knowing:

- **`sellerId` is never read from a request body.** It comes from the verified token. Sending
  one is not an error; it is ignored.
- **You send `workspaceId`.** A seller can have several workspaces, so the API cannot guess.
- Missing or invalid token → `401`.

## Response shape

Success:

```json
{ "data": { ... } }
```

Lists add `meta`, per `apiListResponseSchema`:

```json
{
  "data": [ ... ],
  "meta": { "page": 1, "pageSize": 25, "total": 87 },
  "nextCursor": "eyJwYWdlIjoyfQ"
}
```

Errors are always the same shape, so the dashboard can handle them generically:

```json
{
  "error": {
    "code": "validation_error",
    "message": "Invalid product.",
    "details": { "variants.0.price.amountMinor": ["Expected int, received float"] }
  }
}
```

Both shapes come from `@pakcommerce/shared/api` — `apiDataResponseSchema`,
`apiListResponseSchema` and `apiErrorSchema` — so `apps/web` can parse any response from
this API with the same schemas the API produces them with.

`details` is `Record<field, messages[]>`: several problems with one field collapse into one
entry, so the dashboard can put every message on the input that caused it.

| Status | `code` | When |
|---|---|---|
| 400 | `validation_error` | Body or query does not match the contract, or a check constraint refused it |
| 401 | `unauthorized` | No token, malformed header, or an invalid/expired token |
| 404 | `not_found` | No such product **for you** |
| 409 | `conflict` | Well-formed, but collides with stored data — a duplicate slug or SKU |
| 500 | `internal_error` | A bug. The real message is logged, never returned |

Codes come from `apiErrorCodeSchema`; this API does not invent its own.

### Why 404 and not 403

Asking for another seller's product returns `404`, not `403`. RLS makes the row invisible
rather than forbidden, so "absent" and "not yours" are reported identically. A `403` would
confirm the id exists, which is precisely what someone probing ids wants to learn.

## Endpoints

### `POST /api/v1/products`

Creates a product **and its variants** in one atomic operation. Validated against
`createProductInputSchema` from `@pakcommerce/shared`.

```json
{
  "workspaceId": "…",
  "title": "Lawn Kurta",
  "slug": "lawn-kurta",
  "description": null,
  "status": "draft",
  "tags": ["summer"],
  "variants": [
    { "title": "Medium", "sku": "KURTA-M", "price": { "amountMinor": 250000 } }
  ]
}
```

- `slug` is optional — derived from the title if omitted
- `status` defaults to `draft`
- `searchText` is **generated by the backend**; anything sent is ignored
- Prices are **integer minor units** (paisa). `250000` is Rs 2,500
- At least one variant is required

`201` with the full product. Product and variants insert together: if any variant fails, the
product is not created either.

### `GET /api/v1/products`

Validated against `productSearchQuerySchema`.

| Query param | Notes |
|---|---|
| `workspaceId` | **Required** |
| `query` | Matches the generated search document |
| `statuses` | Comma-separated: `draft,active,archived` |
| `inventoryStates` | Comma-separated: `in_stock,low_stock,out_of_stock,untracked` |
| `categoryIds`, `tags` | Comma-separated; matches any |
| `sort` | `newest`, `updated_desc` (default), `title_asc/desc`, `price_asc/desc`, `stock_asc/desc` |
| `limit` | 1–100, default 25 |
| `cursor` | From the previous response's `nextCursor` |

Returns `ProductListItem`s — summary rows with `variantCount`, `priceRange` and a rolled-up
`inventoryState`, not full products.

**`inventoryState` on a list item**: a product is as available as its most available variant.
One in-stock size means the product reads `in_stock`. `untracked` only wins when nothing is
tracked, so it can never mask a real out-of-stock.

`nextCursor` is `null` on the last page and is deliberately opaque — do not parse it.

**A note on pagination.** Two shared contracts disagree: `productSearchQuerySchema` (domain)
is cursor-based, while `apiListResponseSchema` (transport) requires
`meta: { page, pageSize, total }`. This endpoint satisfies both — the cursor carries a page
number, so you can either page forward with `nextCursor` or jump using `meta`. Worth
resolving properly in the contracts rather than leaving each endpoint to decide.

### `GET /api/v1/products/:id`

Returns the full product with its variants, ordered by `position`.

### `PATCH /api/v1/products/:id`

Validated against `updateProductInputSchema`. Product fields only — variants have their own
task.

`searchText` is **rebuilt**, not appended to: removing a tag removes it from the document.

**The slug does not follow a title change.** A slug is an address; renaming a product must not
silently break every link to it. Change it explicitly if you want it changed.

### `DELETE /api/v1/products/:id`

**Archives.** Sets `status` to `archived` and stamps `archivedAt`. The row stays, and stays
retrievable — orders and inventory history will point at it. A hard delete would cascade to
every variant and lose that history.

Archiving also releases the slug: the unique index excludes archived rows, so the seller can
reuse it.

## Orders

Draft and manual orders, plus confirm/cancel transitions. Auth required. Drafts **never**
touch stock; confirming deducts available stock with a `sale` movement.

### `POST /api/v1/orders`

Creates a draft order with line items and the initial status-history row in one database
transaction (`create_draft_order`). Validated against `createDraftOrderInputSchema`.

Limits: money amounts are capped at 2,147,483,647 minor units (the Postgres `integer` maximum), item
`quantity` at 100,000 per line, and the server rejects a line total, subtotal or total over the money cap
with **400** (`items.<i>.quantity` or `total`). `customer.addressLine` stays optional here for future
channels, but a draft without one cannot be confirmed (`address_required`) and drafts cannot be edited,
so seller-facing UIs and the copilot require it. Order lines are returned ordered by creation time, then id
(`order_items` has no position column, so id only makes the order deterministic).

```json
{
  "workspaceId": "…",
  "channel": "manual",
  "customer": {
    "name": "Ayesha Khan",
    "phone": "+923001112233",
    "city": "Lahore"
  },
  "items": [
    { "productId": "…", "variantId": "…", "quantity": 2 }
  ],
  "note": "WhatsApp intake"
}
```

- `channel` defaults to `manual`; `paymentMethod` defaults to `cod`
- Line prices snapshot from the variant when `unitPrice` is omitted
- `subtotal` / `total` are computed server-side (`total = subtotal + shippingFee`)
- `sellerId` comes from the token; anything sent in the body is ignored
- At least one item is required

`201` with the full `Order` (items included). Stock quantities are unchanged.

| Status | When |
|---|---|
| 400 | Body fails the contract, variant missing from the workspace, or productId/variant mismatch |
| 401 | Missing or invalid token |
| 404 | Workspace invisible under RLS |

### `GET /api/v1/orders`

Validated against `orderSearchQuerySchema`.

| Query param | Notes |
|---|---|
| `workspaceId` | **Required** |
| `query` | Case-insensitive match on customer name, phone, or city |
| `customerId` | Only this customer's orders (the profile's full order history). Another seller's id matches nothing |
| `statuses` | Comma-separated: `draft,confirmed,…` |
| `channels` | Comma-separated: `manual,whatsapp,…` |
| `sort` | `newest`, `updated_desc` (default), `total_asc`, `total_desc` |
| `limit` | 1–100, default 25 |
| `cursor` | From the previous response's `nextCursor` |

Returns `OrderListItem`s (each with its `customerId`) in the list envelope (`data`, `meta`, `nextCursor`).

### `GET /api/v1/orders/:orderId`

Returns an `OrderDetail` (`orderDetailSchema`): every `Order` field plus

- `statusHistory` — `OrderStatusHistory[]`, oldest first (a draft starts with `null → draft`).
- `stockChecks` — for **draft** orders only (`[]` otherwise), one entry per line item:
  `{ variantId, productId, title, variantTitle, needed, available, sufficient }`.
  It applies the same rule as `transition_order_status`: quantities are summed per variant
  (lines sharing a variant each report the combined `needed`), `available = on_hand - reserved`,
  `sufficient = available >= needed`. A variant with `track_inventory = false` or null
  on-hand is skipped by confirm, so it reports `available: null, sufficient: true`.
  It is a read-time snapshot; confirm re-checks under a row lock, so a race can still
  return `400`.

Pass `?workspaceId=…` (required). Another seller's id returns `404`, not `403` — same RLS
posture as products.

### `POST /api/v1/orders/:orderId/transition`

Validated against `transitionOrderStatusInputSchema` (`workspaceId`, `toStatus`, optional
`note`; `orderId` comes from the path).

Enabled today:

| `toStatus` | Effect |
|---|---|
| `cancelled` | Draft → cancelled. No stock change. |
| `confirmed` | Draft → confirmed. Requires a delivery address. Deducts available stock (`on_hand - reserved`) per line and writes a `sale` movement per variant. Insufficient stock → **400**, order stays `draft`. |

Returns the updated `OrderDetail` (same shape as `GET /:orderId`). Ship / return /
cancel-after-confirm are not enabled yet. `POST /api/v1/orders` still returns the plain `Order`.

### Not here yet

| Gap | Detail |
|---|---|
| **Ship / return** | Fulfillment transitions and stock restore come later |
| **Edit draft** | No PATCH; recreate or wait for a later task |
| **Dashboard** | Orders list and detail page are real; the order form (T-040) and overview widgets are not |

Status, `confirmed_at`, and `cancelled_at` cannot be changed with a raw SQL `UPDATE`
(including via the copilot) — only `transition_order_status`.

## Customers

Customer 360: who a customer is, what they have spent, and what happened with them. Auth
required. Contract: `packages/shared/src/customers`.

### How customers exist

There is no `POST /customers`. **The database creates customers from orders.** A trigger on
`orders` (`link_order_to_customer`) runs on every insert, so every path that creates orders
(this API, the copilot tool, future Shopify or WhatsApp sync) is covered:

- **Identity is the normalised phone, and only the phone**, unique per workspace.
  `normalize_phone` (SQL) and `normalizePhone` (shared) apply the same Pakistan rules, tested
  against one fixture table: spaces/dashes/brackets stripped, `00` becomes `+`, `03XXXXXXXXX`,
  `923XXXXXXXXX` and `3XXXXXXXXX` all become `+923XXXXXXXXX`. So `0300-1234567` and
  `+92 300 1234567` are the same customer.
- **An order's phone must contain digits.** `customer.phone` is validated by the order contract
  (**400** with details on `customer.phone`) and by a database check, so a phone like `n/a` is
  refused rather than creating a junk customer.
- The same phone under two sellers is two customers.
- **Email is stored (lower-cased) and searchable, but never used to match orders to
  customers.** Email-only matching arrives with store sync.
- A new order refreshes the customer's latest-known name, city, address and email (a missing
  address or email never erases a known one). **Editing an existing order never changes the
  customer's details.** The order keeps its own snapshot.
- **Fixing a phone typo on an order re-links it**: when an order's normalised phone changes it
  moves to the customer for the new phone (created if needed; an existing customer's details are
  left alone). The customer it left is **deleted if it has no orders and no notes left**.
- `orders.customer_id` is set by the trigger and cannot be edited; `customers.phone` cannot be
  edited either (correct the order instead). The copilot's `mutateDatabase` cannot write
  `customers`; it can still write `customer_notes`.
- Legacy orders from before this existed were backfilled; one whose phone has no digits got its
  own customer keyed `order:<order id>`.

### Spend, counts and tags are computed

Nothing here is stored. The `customer_summary` view (`security_invoker`, so RLS applies)
computes it from orders on every read.

- **Lifetime spend** = sum of order totals in `confirmed`, `shipped` or `delivered`. Drafts,
  cancelled and returned orders are excluded. `averageOrderValue` is the mean over those
  orders, `null` when there are none.
- `totalOrderCount`, `completedOrderCount`, `statusCounts` (one per status), `firstOrderAt` /
  `lastOrderAt` (creation time of the earliest / latest order of any status), `noteCount`,
  `riskNoteCount`.
- **Tags** are derived, and a customer can have several: `first_time` (no completed - confirmed, shipped or delivered - order yet),
  `repeat` (two or more), `has_returns` (at least one returned order), `flagged` (at least one
  risk note).

### `GET /api/v1/customers`

Validated against `customerSearchQuerySchema`.

| Query param | Notes |
|---|---|
| `workspaceId` | **Required** |
| `phone` | Exact match on the normalised phone; whatever format is sent is normalised first (for the WhatsApp agent). **400** if it has no digits |
| `query` | Case-insensitive substring match on name, phone, city or email. `*` is ignored (it is not a wildcard). A phone typed in any format also matches its normalised form (`0300-1234567` finds `+923001234567`); a partial local number such as `0345 111` matches too |
| `tags` | Comma-separated: `first_time,repeat,has_returns,flagged`. Several tags narrow: a customer must have all of them |
| `sort` | `last_order_desc` (default; customers without orders last), `spend_desc`, `name_asc`, `created_desc` |
| `limit` | 1-100, default 25 |
| `cursor` | From the previous response's `nextCursor` |

Returns `CustomerListItem`s (`customer` fields + `summary` + `tags`) in the list envelope
(`data`, `meta`, `nextCursor`).

### `GET /api/v1/customers/context?workspaceId=&phone=` (or `customerId=`)

**The WhatsApp Sales Agent's entry point**: one call returns the compact customer context
(`customerContextSchema`) instead of list + detail. The copilot's `getCustomerProfile` tool
uses the same `getCustomerContext` service function. Bearer auth and RLS as everywhere else.

Provide exactly one of `phone` (any format, normalised first, exact match) or `customerId`.
**URL-encode the phone**: `+` must be sent as `%2B` (`phone=%2B14155552671`), otherwise the `+` arrives as a
space and a foreign number will not match.
`400` if the phone has no digits, if neither or both are given, or if `workspaceId` is missing.
An unknown customer, or another seller's, is **`200` with `{ "data": { "found": false } }`**: the
agent treats the phone as a new customer.

```json
{
  "data": {
    "found": true,
    "customer": { "id": "...", "name": "Ayesha Khan", "phone": "+923001234567", "city": "Lahore" },
    "tags": ["repeat", "flagged"],
    "summary": {
      "lifetimeSpend": { "amountMinor": 500000, "currency": "PKR" },
      "completedOrderCount": 2, "totalOrderCount": 3, "returnedOrderCount": 0,
      "lastOrderAt": "2026-11-14T10:00:00+00:00"
    },
    "recentOrders": [{ "id": "...", "status": "delivered", "total": { "amountMinor": 250000, "currency": "PKR" }, "createdAt": "..." }],
    "riskNotes": [{ "body": "Refused delivery once", "createdAt": "..." }]
  }
}
```

`recentOrders` is the newest 5 orders, `riskNotes` the newest 5 notes of kind `risk`. No email,
address or timeline: it goes into LLM context, so it stays small.

### `GET /api/v1/customers/:customerId?workspaceId=`

Returns a `CustomerDetail`: the list item plus

- `recentOrders` - the last 20 orders as `OrderListItem`s, newest first. The full history is
  `GET /api/v1/orders?customerId=<id>`.
- `notes` - `CustomerNote[]`, newest first, **at most the 50 newest** (`summary.noteCount` is the total).
- `timeline` - newest first, capped at 50: `order_status_changed`
  (`{ orderId, fromStatus | null, toStatus, note, at }`; `fromStatus` is `null` on the initial
  draft creation) and `note_added` (`{ noteId, kind, body, at }`), discriminated on `type`.

Another seller's customer, or an unknown id, returns `404`. A malformed id or a missing
`workspaceId` returns `400`.

### `POST /api/v1/customers/:customerId/notes`

Body: `{ "workspaceId": "...", "kind": "note" | "risk", "body": "..." }`. `kind` defaults to
`note`; `body` is trimmed, 1-2000 characters. A `risk` note makes the customer `flagged`.
`201` with the `CustomerNote`. `404` for a customer the seller cannot see.

### `DELETE /api/v1/customers/:customerId/notes/:noteId?workspaceId=`

Deletes one of the seller's own notes. `204` with no body; `404` if the note does not exist or
belongs to someone else.

## Conversations (WhatsApp inbox)

Shapes come from `@pakcommerce/shared/conversations` (`Conversation`, `Message`). All routes need
a seller token and run through RLS, so another seller's conversation answers `404`.
Conversations are created only by inbound ingestion (`ingest_inbound_message`), never by a seller.

### `GET /api/v1/conversations`

| Query param | Notes |
|---|---|
| `workspaceId` | **Required** |
| `query` | Case-insensitive substring match on buyer name or phone (any phone format; `*` ignored) |
| `states` | Comma-separated: `open,ai_active,waiting_approval,human_takeover,closed` |
| `unreadOnly` | `true` keeps conversations with unread messages |
| `limit` | 1-100, default 25 |
| `cursor` | From the previous response's `nextCursor` |

Ordered `last_message_at desc nulls last, id desc`. Returns `{ data, meta, nextCursor }`.

### `GET /api/v1/conversations/:id?workspaceId=`

`{ data: Conversation }`. `404` when missing or not yours.

### `GET /api/v1/conversations/:id/messages?workspaceId=&limit=&cursor=`

Newest first (`limit` 1-200, default 50). `{ data, meta, nextCursor }`; `nextCursor` loads older messages.

### `POST /api/v1/conversations/:id/read?workspaceId=`

Sets `unreadCount` to 0 and returns `{ data: Conversation }`.

### `POST /api/v1/conversations/:id/state`

Seller state change: take over, hand back to the AI, turn AI off, close. Body:
`{ "workspaceId": "uuid", "to": "human_takeover", "reason": "optional, up to 500 chars" }`.
The actor is always `seller` (`assertConversationTransition`); `reason` is stored in `handoffReason`
only when `to` is `human_takeover`. Returns `{ data: Conversation }`. `409` for a move a seller may
not make, or when another tab changed the state first (the update is conditional on the state that
was read); `404` when not found or not yours.

### `POST /api/v1/conversations/mock-inbound`

Fakes a Twilio inbound WhatsApp message so the inbox can be demoed before Twilio is connected.
Returns `404` unless `ENABLE_MOCK_INBOUND` is on (default in development/test; explicit in production, see RUNBOOK).

```json
{
  "workspaceId": "uuid",
  "From": "whatsapp:+923001234567",
  "ProfileName": "Ayesha",
  "Body": "Salam, is this kurta available?",
  "MessageSid": "SM...",
  "NumMedia": 1,
  "MediaUrl0": "https://example.com/photo.jpg",
  "MediaContentType0": "image/jpeg",
  "aiEnabled": false
}
```

`MessageSid` is generated (`SMmock...`) when absent; a repeated `MessageSid` returns the original
message with `duplicate: true` and changes nothing. `NumMedia`/`MediaUrl{n}`/`MediaContentType{n}`
are optional (up to 10, https URLs only). `Body` up to 4096 characters; a message needs text or media.
The caller must own `workspaceId` (checked with their own token before any write; otherwise `404`).

`201` (new) or `200` (duplicate): `{ data: { conversationId, messageId, duplicate, state } }`.
`state` is the thread state after ingest: a new thread starts `ai_active` when AI replies are on, else
`open`; a closed thread reopens; live threads keep their state. `aiEnabled` is optional: when omitted
the workspace's sales agent setting is used (below).

### AI reply pipeline

After a **new** (non-duplicate) inbound message is stored in an `ai_active` conversation, the API runs
an agent turn in the background (the webhook/mock response does not wait). Turns for one conversation
run one at a time, in order. A turn calls `POST ${ML_URL}/agent/respond` (Bearer `AGENT_SERVICE_TOKEN`,
45 s timeout) with the message, the last 20 messages (role and text only, no phones) and the policy text.
The reply is sent through the active WhatsApp provider (`WHATSAPP_PROVIDER=simulator` fakes it) and stored
as an outbound `ai` message (`sent`, or `failed`); it is dropped if the state is no longer `ai_active`.
`handoff.required`, an unreachable or invalid agent, or missing config moves the conversation
`ai_active -> human_takeover` with a short `handoffReason` (for example "Buyer wants to order",
"AI unavailable"); a reply that comes with a handoff is sent first.

### `GET /api/v1/sales-agent/settings?workspaceId=`

`{ data: { workspaceId, aiEnabled, policyText } }`. Defaults (`false`, `""`) when never saved.
`404` for a workspace that is not yours.

### `PUT /api/v1/sales-agent/settings`

Body `{ "workspaceId": "uuid", "aiEnabled": true, "policyText": "up to 4000 chars" }`. Returns the saved
settings. `aiEnabled` decides whether new and reopened conversations start `ai_active`; `policyText`
(delivery, returns, payment/COD) is the only policy text the agent may quote. `400` on invalid input, `404` for
a foreign workspace.

## Limitations

Honest list of what this does not do yet.

| Limitation | Detail |
|---|---|
| **Images** | The `product_images` table exists and the shared contract includes `productImageSchema`, but the product API does not expose dedicated image CRUD endpoints yet. Images are not written or returned through the product endpoints. |
| **Variant editing** | `PATCH` updates product fields only. Adding, editing or removing variants after creation needs its own endpoints. |
| **Search quality** | `query` is a case-insensitive substring match on the generated document. No stemming, no ranking, no full-text index. |
| **Pagination** | Offset behind an opaque cursor. Fine for a seller's catalogue; degrades on very large ones. |
| **Rate limiting** | None. |

## Inventory

Stock adjustments and their history. Auth required on both endpoints.

### `POST /api/v1/inventory/adjustments`

Sets a variant's stock to a new total and records why. Validated against
`adjustStockInputSchema` from `@pakcommerce/shared`.

```json
{
  "workspaceId": "…",
  "variantId": "…",
  "targetQuantityOnHand": 25,
  "reason": "purchase",
  "note": "Eid restock"
}
```

- **You send the new total, not a change.** "Set it to 25" is what a seller counting a shelf
  knows. The backend derives the delta from the current quantity.
- `reason` is required: `purchase`, `sale`, `return`, `manual_adjustment`, `correction` or
  `damage_loss`.
- `note` is optional, up to 500 characters.
- The acting user comes from the token. Sending `performedBy` or `sellerId` is ignored.

`201` with both the inventory as it now stands and the movement that recorded the change
(`stockAdjustmentResultSchema`):

```json
{
  "data": {
    "inventory": { "variantId": "…", "quantityOnHand": 25, "reservedQuantity": 0, "state": "in_stock" },
    "movement": {
      "reason": "purchase",
      "quantityDelta": 15,
      "beforeQuantityOnHand": 10,
      "afterQuantityOnHand": 25,
      "performedBy": "…"
    }
  }
}
```

The quantity and the movement are written in **one database transaction** (the
`adjust_stock` function), against a locked row. Stock cannot change without a movement, a
movement cannot describe a change that did not happen, and two adjustments arriving together
chain instead of both starting from the same number.

| Status | When | `details` field |
|---|---|---|
| 400 | Target is negative or not a whole number | `targetQuantityOnHand` |
| 400 | Target is below the units already reserved for orders | `targetQuantityOnHand` |
| 400 | Target equals the current quantity - nothing to record | `targetQuantityOnHand` |
| 400 | The variant does not track stock | `variantId` |
| 400 | Missing or unknown `reason` | `reason` |
| 404 | No such variant in that workspace **for you** | |

A refused adjustment writes nothing: no quantity change and no movement.

### `GET /api/v1/inventory/movements`

The stock history, newest first. Validated against `stockMovementSearchQuerySchema`.

| Query param | Notes |
|---|---|
| `workspaceId` | **Required** |
| `variantId` | Only this variant's movements |
| `reasons` | Comma-separated, matches any: `sale,damage_loss` |
| `limit` | 1–100, default 25 |
| `cursor` | From the previous response's `nextCursor` |

Returns `StockMovement`s in the list envelope, with `meta` and `nextCursor` exactly as the
product list does. Movements are immutable: there is no endpoint to edit or delete one, and
the database refuses both.

### Not here yet

| Gap | Detail |
|---|---|
| **Inventory list** | No `GET /api/v1/inventory`. Read stock through the product endpoints for now. |
| **Other writers** | Stock set through the product API (initial stock on create, and product updates) is still written to `quantity_on_hand` directly with no movement. The copilot's `updateProductStock` goes through `adjust_stock`, and `mutateDatabase` is refused by the database if it tries to change stock. |
| **Reservations** | Confirmation deducts `quantity_on_hand` via `sale`; it does not bump `reserved_quantity`. Soft-reserve-on-confirm can come later if the model changes. |

## Rafiq (seller copilot) chats

Seller-facing name is **Rafiq**. Routes and tables stay `copilot`. Auth required on every endpoint below.

| Method | Path | What it does |
|---|---|---|
| `GET` | `/api/v1/copilot/chats` | Recent chats (`archived_at` is null). Pass `?archived=1` for archived. |
| `POST` | `/api/v1/copilot/chats` | Create an empty chat. Returns `{ id, title, updatedAt, archivedAt }`. |
| `GET` | `/api/v1/copilot/chats/:id` | Load one chat’s `UIMessage[]` transcript. |
| `POST` | `/api/v1/copilot/chats/:id/archive` | Soft-archive (sets `archived_at`). |
| `POST` | `/api/v1/copilot/chats/:id/unarchive` | Restore from archive. |
| `DELETE` | `/api/v1/copilot/chats/:id` | Hard delete. |
| `POST` | `/api/v1/copilot/chat` | Stream one turn. Body: `{ id, message }` (last `UIMessage` only). Server loads history, merges, streams, and saves. |

Persistence is the Vercel AI SDK `UIMessage[]` in `public.copilot_chats.messages` (jsonb). The first save that has a user message asks the model for a short sidebar title once. RLS scopes every row to `seller_id = auth.uid()`.

## Tool registry and the sales-agent API

Business tools are defined once in `apps/api/src/tools/` and shared by two callers: Rafiq (in-process) and the WhatsApp sales agent (`apps/ml`, over HTTP). A definition is provider-neutral (no Vercel AI SDK, no LLM vendor):

```ts
{ name, description, inputSchema /* zod */, outputSchema?,
  permission: "read" | "write", owner: "catalog" | "inventory" | "orders" | "customers" | ...,
  audiences: ("copilot" | "sales_agent")[], needsApproval: boolean,
  audit: { redact?: string[] },            // dotted input paths masked in the audit row
  execute(ctx, input) }                    // ctx: { db, workspaceId, sellerId, actor, audience, conversationId, audit }
```

- `registerTool`, `getTools({ audience })`, `getTool(name)`: names are unique (a duplicate throws). `toolInputJsonSchema` exports the input as JSON Schema via zod's `z.toJSONSchema`.
- Add a tool in `tools/definitions.ts`. Existing copilot tools wrap their original `*Tool(auth)` factories, so their behaviour is unchanged.
- The copilot builds its Vercel AI SDK tools and the `"user-approval"` map from the registry in `copilot/ai-sdk-adapter.ts`. That file is the only place the SDK meets the registry.
- `runTool` is the single entry point for both callers: it validates, executes and writes the audit row.

### Audit

Every call writes one row to `ai_tool_calls` (service role; a seller may `select` only their own rows, and cannot insert, update or delete): tool name, audience, actor (`seller` for the copilot, `ai` for the sales agent), seller, workspace (null for copilot), conversation, ok, error code, duration, and the input with the tool's `audit.redact` paths masked. An audit failure never fails the tool call.

### Sales-agent HTTP contract

Service-to-service, not seller auth. Header `Authorization: Bearer ${AGENT_SERVICE_TOKEN}` (constant-time compare). With `AGENT_SERVICE_TOKEN` unset every route below answers `404`. Missing or wrong token: `401`. All errors on this surface are `{ "ok": false, "error": { "code", "message" } }`.

`GET /api/v1/agent/tools` returns `{ "data": [{ name, description, permission, owner, needsApproval, inputSchema }] }` (`inputSchema` is JSON Schema), only for tools with audience `sales_agent`. Today: `searchProducts` and `checkInventory`.

`POST /api/v1/agent/tools/:name` with body `{ "conversationId": "<uuid>", "input": { ... } }` returns `200 { "ok": true, "output": ... }` or `{ "ok": false, "error": { "code", "message" } }`:

| Status | code | When |
| --- | --- | --- |
| 400 | `invalid_request` / `invalid_input` | Body is not `{ conversationId, input }`, or `input` fails the tool's schema |
| 401 | `unauthorized` | Missing or wrong token |
| 403 | `ai_not_allowed` | A `write` tool while the conversation is not `ai_active` (`aiMayReply`) |
| 403 | `approval_required` | The tool has `needsApproval` (not available to the agent yet; draft orders arrive in S11) |
| 404 | `unknown_tool` / `conversation_not_found` / tool-specific (e.g. `product_not_found`) | Unknown or copilot-only tool, no such conversation |
| 422 | tool-specific | The tool refused (e.g. `search_failed`) |
| 500 | `internal_error` | Unexpected failure (details are logged, not returned) |

The workspace and seller are read from the conversation row; the caller cannot supply or override them. The agent's tools read the live catalogue only (active products and variants) and return no buyer data.

- `searchProducts` input: `{ query?, statuses?, inventoryStates?, categoryIds?, tags?, sort?, limit? }` (same as the copilot, but `statuses` is forced to `active`). Output: `{ total, products: [{ productId, name, priceFromPkr, priceToPkr, inStock, variants: [{ variantId, label, pricePkr, inStock, quantity }] }] }`.
- `checkInventory` input: `{ productId, size?, colour? }`. Output: `{ productId, name, availableSizes, availableColours, anyInStock, variants: [...] }`. `quantity` is a bucket: `none`, `1-3`, `4-10`, `10+` or `untracked`; exact counts are not exposed.

## Copilot tools

The chat turn at `POST /api/v1/copilot/chat` (auth required, streams via the Vercel AI SDK) exposes tools the model can call to ground answers in the seller's real data and execute guarded business mutations:

| Tool | What it does | Safety |
|---|---|---|
| `searchProducts` | Structured search over the seller's catalogue (text, status, inventory state, tags, sort). Returns `ProductListItem[]` validated against the shared contract. | Reuses the product service + RLS; the model never supplies a `workspaceId` — it is resolved from the seller context. |
| `getCustomerProfile` | Compact profile of one customer by `phone` (any format) or `customerId` (exactly one): tags, lifetime spend, order and returned counts, last 5 orders, risk notes. Returns the `customerContext` shape; `{ found: false, message }` for an unknown customer. | Read-only, no approval. Same `getCustomerContext` as `GET /customers/context`; the workspace is the seller's current one, never model-supplied. |
| `getSchema` | Lists the seller's queryable tables and their real columns/types, so the model can confirm what exists before writing SQL. | Runs a fixed introspection query (never model-authored) through `run_readonly_query`; input capped to the owned tables by an enum. |
| `queryDatabase` | Executes a single read-only SELECT the model wrote, for questions no structured tool covers. | Runs via the `run_readonly_query` Postgres function (SECURITY INVOKER) in a **read-only transaction**: RLS applies, nothing can be written (not even through a function call), semicolons, mutating keywords, `set_config` and functions that run SQL from a string (`query_to_xml`, `ts_stat`, …) are rejected, bounded to 10s / 200 rows. |
| `getCourierPerformance` | City delivery metrics. **Demo stub** — returns fixed sample values until courier data exists. | Read-only. |
| `mutateDatabase` | Universal guarded write-side mutation tool (UPDATE, INSERT, DELETE). Enables modifying any catalogue or inventory attribute. | Strictly requires Human-in-the-Loop (`user-approval`) in the UI before execution. Runs via `run_guarded_mutation` (SECURITY INVOKER) with Postgres RLS; destructive DDL (`DROP`, `ALTER`, `TRUNCATE`) is forbidden, and so are `set_config`, functions that run SQL from a string, `U&` escapes and `transition_order_status`, so it cannot fake the seller's identity or change an order's status. Triggers also refuse any write it makes to `orders`, `order_items`, `order_status_history` or `stock_movements`, and any change to a variant's `quantity_on_hand` / `reserved_quantity`. |
| `updateProductStock` | Updates quantity on hand for a variant. | Requires Human-in-the-Loop (`user-approval`). Updates `product_variants` directly via caller's authenticated RLS client. |
| `updateProductPrice` | Updates selling price and compare-at price in PKR. | Requires Human-in-the-Loop (`user-approval`). Updates `product_variants` directly via caller's authenticated RLS client. |
| `updateProductDetails` | Updates product title, description, status, or tags. | Requires Human-in-the-Loop (`user-approval`). Updates `products` directly via caller's authenticated RLS client. |
| `createDraftOrder` | Creates a **draft** order for a customer (customer name/phone/city/address line, optional email, `items[{variantId, productId, quantity}]`, optional `channel`, `paymentMethod`, `shippingFee` in PKR minor units, `note`). Returns `{ status, orderId, orderStatus: "draft", total, itemCount, message }`. | Requires Human-in-the-Loop (`user-approval`). Calls the same `createDraftOrder` order service as `POST /orders`: the workspace is the seller's current one (as `GET /workspaces/current`, never model-supplied), variants resolve under RLS, and prices are snapshotted server-side. The input has no status, price, title, sku or total, so it can only create drafts, never confirms or cancels, and does not touch stock. The seller confirms from the Orders page. |

Tools are built per request from the seller context (`createCopilotTools(auth)`), so a seller can only ever read or mutate their own data through them — the same RLS boundary as the REST endpoints.

### How the model writes correct SQL and executes actions

1. **Schema in the system prompt.** The copilot prompt embeds the real schema (tables, columns, types, the "money is integer paisa" rule, the note that `inventory_state` is generated). A model that can see `price_amount_minor` stops guessing `price`. Kept honest by a drift-guard test that pins the document to the migrations (`schema-document.test.ts`).
2. **Runtime introspection.** `getSchema` queries `information_schema` through the safe read-only RPC, so the model can confirm a column exists even if the prompt document is stale.
3. **Execution-feedback retry loop.** `streamText` runs with `stopWhen: isStepCount(8)`. When SQL execution fails, the Postgres error is returned to the model as a structured tool result, and the model corrects the SQL and retries.
4. **Native Vercel AI SDK Human-in-the-Loop (HITL) approvals.** All write actions halt with `toolApproval: 'user-approval'` (and `needsApproval` on the write tools). The dashboard shows a seller-facing Yes / No card — no SQL. The mutation commits only after the seller clicks Yes.
5. **Seller speech in tool args.** `searchProducts` maps Live→`active`, Hidden→`archived`, low/finished→stock enums, and coerces string limits so the first tool call does not fail Zod validation.

### Future Architecture / Deferred: Intent-Based Schema Partitioning

As the database grows larger with subsequent slices (orders, shipments, payouts, discounts, customers, conversations), embedding the entire database schema into the system prompt or returning every table in a single `getSchema` call will make the context window excessively heavy, increase token latency, and introduce hallucinations.

**Planned Architecture:**
- **Domain / Intent Slicing:** Partition database tables by functional intent (e.g. `catalog_inventory`, `orders_logistics`, `marketing_discounts`, `finance_analytics`).
- **Dynamic Schema Slicing:** `getSchema` will accept an `intent` or `domain` parameter (or classify the user prompt), returning only the tables, columns, and foreign keys relevant to that specific request rather than the entire database.

This is the later form of schema selection. It is not useful while the database is five tables. See the research note below.

### Deferred: decision models

**Not required now.** The catalogue copilot is a single `streamText` loop. Record the slots here so a later slice can add a decision model without redesigning that loop.

A decision model returns a typed choice, a score, or a yes/no with a probability. It does not write SQL and it does not write the sentence the seller reads. [Jev](https://vercel.com/i/jev-agent-control) (TypeSafe, model id `typesafe-ai/jev`, AI SDK `experimental_evaluate`) is one implementation. A small chat model forced to a structured output can sit in the same slots. Application code still authorizes every tool call. A probability is not a permission.

| Slot | Question | What the code would do | Leave alone |
|---|---|---|---|
| Before `streamText` in `copilot-router.ts` | Catalogue, analytics SQL, a write, or not answerable yet | Catalogue calls `searchProducts` only. SQL is the only path that receives `queryDatabase` and the schema document. Writes receive the typed update tools. Orders, COD, and couriers are refused until those tables exist. | The written answer |
| The `tools` object for that request | Which tools this turn may call | Hide `mutateDatabase` when `updateProductStock`, `updateProductPrice`, or `updateProductDetails` can express the change. Hide `getCourierPerformance` until it reads a real table. | RLS and the SQL sandbox |
| After `queryDatabase` returns an error | Retry once, or stop and tell the seller | One correction step for a bad column name. Stop when the same database error comes back. | The eight-step cap, which stays as the hard budget |
| The approval card | Routine single-SKU edit, or a broad or destructive change | Both still wait for Approve. The card shows the score. | `toolApproval: "user-approval"`. The decision model must not approve stock or price changes |
| `getLanguageModel()` in `provider.ts` | Small model, or the model that writes joins | One provider key. The pick is per request. | Provider credentials |

The same yes/no fits the WhatsApp agent later, for “hand this conversation to a person.” There is no agent loop there yet.

Offline, the same judge can score a fixed set of seller questions: right tool, numbers copied from the tool result, write not executed before approval, out-of-scope question refused. That set does not exist yet. Unit tests only show that the tools are wired.

### What the current loop already takes from the research

Checked October 2026. The loop is the current production pattern, not an older one that has been replaced.

- **Schema in the prompt, plus executing the SQL and feeding the error back.** CHESS (Talaei et al., Stanford, 2024) found that removing the revision step cost 6.80 execution-accuracy points on their BIRD subsample. This copilot’s retry is that idea in the cheap form: one query, the database error, one correction. CHESS itself is several model stages (retrieve, select a schema, generate, revise). That stack is for benchmark-scale databases, not a seller chat.
- **Sending the whole schema.** The same line of work, including Distillery (Maamari et al., 2024) as discussed in the CHESS follow-up, finds that a modern model can take a schema on the order of a hundred columns without a separate linking step. Linking starts to pay off around thousands of columns (their synthetic schema of 4,337 columns gained about 2 points from a schema-selection agent). Five tables do not need that. Intent partitioning above is the note for when orders and shipments arrive.
- **A person approves writes, and tools stay narrow.** Vercel’s 2026 production guidance is the same rule this API already enforces with `toolApproval`, and it warns that overlapping tools and an open-ended writer increase wrong calls. `mutateDatabase` beside the three typed update tools is the known weak spot. A decision model can hide it later. Removing the overlap does not require Jev.
- **Durable workflows and a tool-protocol gateway.** `WorkflowAgent` matters when an approval must survive a crashed request. This approval lives in the open chat. A Model Context Protocol gateway matters at thousands of tools. This route has eight.

TypeSafe’s speed and cost figures for Jev are the vendor’s claim. They are not a measurement on this repository, and they are not a reason to replace the chat model.

## Trying it by hand

Get a token (browser console on a signed-in dashboard, or via the Supabase client):

```js
const { data } = await supabase.auth.signInWithPassword({ email, password });
console.log(data.session.access_token);
```

Then:

```bash
TOKEN="…"
WORKSPACE="…"

curl -s http://localhost:4000/api/v1/products \
  -H "Authorization: Bearer $TOKEN" \
  -H "Content-Type: application/json" \
  -d "{\"workspaceId\":\"$WORKSPACE\",\"title\":\"Lawn Kurta\",
       \"variants\":[{\"title\":\"Medium\",\"price\":{\"amountMinor\":250000}}]}"

curl -s "http://localhost:4000/api/v1/products?workspaceId=$WORKSPACE" \
  -H "Authorization: Bearer $TOKEN"
```

Without the header both return `401`. With another seller's product id, `404`.
