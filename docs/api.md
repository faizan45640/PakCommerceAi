# API Reference

The Express backend in `apps/api`, running on port 4000.

Base path: `/api/v1`

---

## Authentication

Every endpoint below `/api/v1/products` requires a Supabase access token:

```http
Authorization: Bearer <access_token>
```

The token is the one `supabase.auth.signInWithPassword()` returns in the browser. The API
verifies it with Supabase — it does not decode and trust it locally — and then builds a
**request-scoped database client that carries it**.

That last part is the whole design. The API does **not** filter results by seller. It hands
the seller's identity to Postgres, and the RLS policies written in the migrations do the
filtering. There is no `where seller_id = …` anywhere in the product code, and there must
never be one: that would turn a rule the database enforces into a rule a developer has to
remember on every query.

Consequences worth knowing:

- **`sellerId` is never read from a request body.** It comes from the verified token. Sending
  one is not an error; it is ignored.
- **You send `workspaceId`.** A seller can have several workspaces, so the API cannot guess.
- Missing or invalid token → `401`.

## Response shape

Success:

```json
{ "data": { ... } }
```

Lists add `meta`, per `apiListResponseSchema`:

```json
{
  "data": [ ... ],
  "meta": { "page": 1, "pageSize": 25, "total": 87 },
  "nextCursor": "eyJwYWdlIjoyfQ"
}
```

Errors are always the same shape, so the dashboard can handle them generically:

```json
{
  "error": {
    "code": "validation_error",
    "message": "Invalid product.",
    "details": { "variants.0.price.amountMinor": ["Expected int, received float"] }
  }
}
```

Both shapes come from `@pakcommerce/shared/api` — `apiDataResponseSchema`,
`apiListResponseSchema` and `apiErrorSchema` — so `apps/web` can parse any response from
this API with the same schemas the API produces them with.

`details` is `Record<field, messages[]>`: several problems with one field collapse into one
entry, so the dashboard can put every message on the input that caused it.

| Status | `code` | When |
|---|---|---|
| 400 | `validation_error` | Body or query does not match the contract, or a check constraint refused it |
| 401 | `unauthorized` | No token, malformed header, or an invalid/expired token |
| 404 | `not_found` | No such product **for you** |
| 409 | `conflict` | Well-formed, but collides with stored data — a duplicate slug or SKU |
| 500 | `internal_error` | A bug. The real message is logged, never returned |

Codes come from `apiErrorCodeSchema`; this API does not invent its own.

### Why 404 and not 403

Asking for another seller's product returns `404`, not `403`. RLS makes the row invisible
rather than forbidden, so "absent" and "not yours" are reported identically. A `403` would
confirm the id exists, which is precisely what someone probing ids wants to learn.

## Endpoints

### `POST /api/v1/products`

Creates a product **and its variants** in one atomic operation. Validated against
`createProductInputSchema` from `@pakcommerce/shared`.

```json
{
  "workspaceId": "…",
  "title": "Lawn Kurta",
  "slug": "lawn-kurta",
  "description": null,
  "status": "draft",
  "tags": ["summer"],
  "variants": [
    { "title": "Medium", "sku": "KURTA-M", "price": { "amountMinor": 250000 } }
  ]
}
```

- `slug` is optional — derived from the title if omitted
- `status` defaults to `draft`
- `searchText` is **generated by the backend**; anything sent is ignored
- Prices are **integer minor units** (paisa). `250000` is Rs 2,500
- At least one variant is required

`201` with the full product. Product and variants insert together: if any variant fails, the
product is not created either.

### `GET /api/v1/products`

Validated against `productSearchQuerySchema`.

| Query param | Notes |
|---|---|
| `workspaceId` | **Required** |
| `query` | Matches the generated search document |
| `statuses` | Comma-separated: `draft,active,archived` |
| `inventoryStates` | Comma-separated: `in_stock,low_stock,out_of_stock,untracked` |
| `categoryIds`, `tags` | Comma-separated; matches any |
| `sort` | `newest`, `updated_desc` (default), `title_asc/desc`, `price_asc/desc`, `stock_asc/desc` |
| `limit` | 1–100, default 25 |
| `cursor` | From the previous response's `nextCursor` |

Returns `ProductListItem`s — summary rows with `variantCount`, `priceRange` and a rolled-up
`inventoryState`, not full products.

**`inventoryState` on a list item**: a product is as available as its most available variant.
One in-stock size means the product reads `in_stock`. `untracked` only wins when nothing is
tracked, so it can never mask a real out-of-stock.

`nextCursor` is `null` on the last page and is deliberately opaque — do not parse it.

**A note on pagination.** Two shared contracts disagree: `productSearchQuerySchema` (domain)
is cursor-based, while `apiListResponseSchema` (transport) requires
`meta: { page, pageSize, total }`. This endpoint satisfies both — the cursor carries a page
number, so you can either page forward with `nextCursor` or jump using `meta`. Worth
resolving properly in the contracts rather than leaving each endpoint to decide.

### `GET /api/v1/products/:id`

Returns the full product with its variants, ordered by `position`.

### `PATCH /api/v1/products/:id`

Validated against `updateProductInputSchema`. Product fields only — variants have their own
task.

`searchText` is **rebuilt**, not appended to: removing a tag removes it from the document.

**The slug does not follow a title change.** A slug is an address; renaming a product must not
silently break every link to it. Change it explicitly if you want it changed.

### `DELETE /api/v1/products/:id`

**Archives.** Sets `status` to `archived` and stamps `archivedAt`. The row stays, and stays
retrievable — orders and inventory history will point at it. A hard delete would cascade to
every variant and lose that history.

Archiving also releases the slug: the unique index excludes archived rows, so the seller can
reuse it.

## Limitations

Honest list of what this does not do yet.

| Limitation | Detail |
|---|---|
| **Images** | There is no `product_images` table. Products always return `images: []` and `primaryImage: null`. Sending a non-empty `images` array returns `400` rather than silently dropping it — `apiErrorCodeSchema` has no "not implemented" code and inventing one would break the shared contract. |
| **Variant editing** | `PATCH` updates product fields only. Adding, editing or removing variants after creation needs its own endpoints. |
| **Search quality** | `query` is a case-insensitive substring match on the generated document. No stemming, no ranking, no full-text index. |
| **Pagination** | Offset behind an opaque cursor. Fine for a seller's catalogue; degrades on very large ones. |
| **Rate limiting** | None. |

## Copilot tools

The copilot at `POST /api/v1/copilot/chat` (auth required, streams via the Vercel AI SDK) exposes tools the model can call to ground answers in the seller's real data:

| Tool | What it does | Safety |
|---|---|---|
| `searchProducts` | Structured search over the seller's catalogue (text, status, inventory state, tags, sort). Returns `ProductListItem[]` validated against the shared contract. | Reuses the product service + RLS; the model never supplies a `workspaceId` — it is resolved from the seller context. |
| `getSchema` | Lists the seller's queryable tables and their real columns/types, so the model can confirm what exists before writing SQL. | Runs a fixed introspection query (never model-authored) through `run_readonly_query`; input capped to the owned tables by an enum. |
| `queryDatabase` | Executes a single read-only SELECT the model wrote, for questions no structured tool covers. | Runs via the `run_readonly_query` Postgres function (SECURITY INVOKER): RLS applies, semicolons and mutating keywords are rejected, bounded to 10s / 200 rows. |
| `getCourierPerformance` | City delivery metrics. **Demo stub** — returns fixed sample values until courier data exists. | Read-only. |
| `updateProductStock` | Stock adjustment request. **Scaffold** — returns a confirmation card; the mutation itself lands with the inventory task. | Write-side; intentionally returns a confirmation request rather than mutating. |

Tools are built per request from the seller context (`createCopilotTools(auth)`), so a seller can only ever read their own data through them — the same RLS boundary as the REST endpoints.

### How the model writes correct SQL

Three mechanisms work together:

1. **Schema in the system prompt.** The copilot prompt embeds the real schema (tables, columns, types, the "money is integer paisa" rule, the note that `inventory_state` is generated). A model that can see `price_amount_minor` stops guessing `price`. Kept honest by a drift-guard test that pins the document to the migrations (`schema-document.test.ts`).
2. **Runtime introspection.** `getSchema` queries `information_schema` through the safe read-only RPC, so the model can confirm a column exists even if the prompt document is stale.
3. **A bounded retry loop.** `streamText` runs with `stopWhen: isStepCount(3)`. When `queryDatabase` fails, the Postgres error is returned to the model as a structured tool result, and the model corrects the SQL and retries — up to 3 steps, so a confused model cannot run away. This execution-feedback loop is the biggest reliability win for text-to-SQL.

## Trying it by hand

Get a token (browser console on a signed-in dashboard, or via the Supabase client):

```js
const { data } = await supabase.auth.signInWithPassword({ email, password });
console.log(data.session.access_token);
```

Then:

```bash
TOKEN="…"
WORKSPACE="…"

curl -s http://localhost:4000/api/v1/products \
  -H "Authorization: Bearer $TOKEN" \
  -H "Content-Type: application/json" \
  -d "{\"workspaceId\":\"$WORKSPACE\",\"title\":\"Lawn Kurta\",
       \"variants\":[{\"title\":\"Medium\",\"price\":{\"amountMinor\":250000}}]}"

curl -s "http://localhost:4000/api/v1/products?workspaceId=$WORKSPACE" \
  -H "Authorization: Bearer $TOKEN"
```

Without the header both return `401`. With another seller's product id, `404`.
